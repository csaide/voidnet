# HTTP 1.0 + 1.1 Server Support Design

## Overview

Add HTTP/1.0 and HTTP/1.1 server support to the existing `src/net/http/` module, building on the current HTTP/0.9 implementation. Client support is out of scope and will be added later.

## Approach

**Trait-based codec with shared parsing (Approach C):** Extract common HTTP/1.x parsing (request line, headers, body framing) into shared functions in `codec/parse.rs`. Version-specific codecs (`v1_0.rs`, `v1_1.rs`) compose these shared pieces but differ in their state machines and behavioral rules.

## Scope

- Server-only (no client)
- Full method set: GET, HEAD, POST, PUT, DELETE, OPTIONS, TRACE, CONNECT, PATCH
- Content-Length + chunked Transfer-Encoding for request bodies
- Expect: 100-continue support
- Content-Length + auto-chunked responses
- No HTTP pipelining (if a client pipelines requests, they will be processed sequentially — functionally correct but no optimized parallel handling)
- Spec-default keep-alive behavior (1.0 defaults close, 1.1 defaults keep-alive)
- Zero-copy header storage via offset pairs

## Section 1: Version Detection & Codec Dispatch

Detection via request line format:
- HTTP/0.9: `GET /path\r\n` (no version token)
- HTTP/1.0: `GET /path HTTP/1.0\r\n`
- HTTP/1.1: `GET /path HTTP/1.1\r\n`

A `detect_version()` shared function performs a **non-consuming peek** at the first request line in the buffer. It scans for `\r\n` without advancing any buffer state. If a third space-separated token matching `HTTP/1.0` or `HTTP/1.1` is present, the corresponding codec is selected. Otherwise fall back to 0.9. If no `\r\n` is found yet, returns `Incomplete` — the connection reads more data and retries detection. Version is locked per connection.

```rust
pub enum HttpCodec {
    Detecting,
    Http09(Http09Codec),
    Http10(Http10Codec),
    Http11(Http11Codec),
}
```

`Detecting` state delegates to `detect_version()`. On success, the enum transitions to the detected codec and the **same buffer contents** are then passed to that codec's `decode()` for the full parse — no bytes are consumed during detection. On `Incomplete`, the connection reads more data and retries.

## Section 2: Shared Parsing Layer

New file `codec/parse.rs` with functions shared between 1.0 and 1.1:

- **`parse_request_line(buf, buf_offset)`** — finds `\r\n`, splits by spaces, returns `(Method, path_start, path_end, Version, consumed)`. Zero-copy path offsets.
- **`parse_headers(buf, buf_offset, start)`** — parses `Name: Value\r\n` lines until empty `\r\n`. Returns `Vec<HeaderOffset>` with absolute offsets. Max 64 headers enforced.
- **`parse_method(token)`** — maps string to `Method` enum.
- **`find_content_length(headers, buf)`** — scans headers for Content-Length, parses value.
- **`has_header(headers, buf, name)`** — case-insensitive header name scan.

Version-specific codecs call these and layer their own logic on top. Specifically, the HTTP/1.1 codec validates `Host` header presence after `parse_headers()` and returns `ParseError::MissingHostHeader` if absent (RFC 9112 Section 3.2).

## Section 3: Request & Method Changes

**Method enum** expands to full set:

```rust
pub enum Method {
    Get, Head, Post, Put, Delete, Options, Trace, Connect, Patch,
}
```

**Version enum** gains variants:

```rust
pub enum Version {
    Http09, Http10, Http11,
}
```

**Request struct** grows:

```rust
pub struct Request {
    pub method: Method,
    pub path_start: usize,
    pub path_end: usize,
    pub version: Version,
    pub headers: Vec<HeaderOffset>,
    pub body_framing: BodyFraming,
}
```

No longer `Copy` (due to Vec), remains `Clone + Debug`. This is a breaking change — existing tests that rely on `Request` being `Copy` or construct `Request::new()` without the new fields will need updating.

**HeaderOffset** — zero-copy, `Copy` type:

```rust
#[derive(Copy, Clone, Debug)]
pub struct HeaderOffset {
    pub name_start: usize,
    pub name_end: usize,
    pub value_start: usize,
    pub value_end: usize,
}
```

**BodyFraming enum:**

```rust
pub enum BodyFraming {
    None,
    ContentLength(usize),
    Chunked,
}
```

Request gains `header_value(&self, buf: &[u8], name: &str) -> Option<&[u8]>` for case-insensitive lookup.

## Section 4: Body Reading

**Sequential access model:** The handler must fully consume (or discard) the request body via `BodyReader` before writing the response via `ResponseWriter`. This avoids borrow conflicts — both need access to the connection's `TcpStream` and `ReadBuffer`, but never simultaneously. The session state machine enforces this: `ReadingBody` must transition to `ResponseInProgress` before `ResponseWriter` becomes available.

**BodyReader<'conn>** borrows connection internals (shared `&TcpStream` ref — the underlying stream supports `read()` on `&self`):

```rust
pub struct BodyReader<'conn> {
    stream: &'conn TcpStream,
    read_buf: &'conn mut ReadBuffer,
    framing: BodyFraming,
    remaining: usize,
    chunk_state: ChunkState,
    finished: bool,
}
```

**ChunkState** for chunked decoding:

```rust
enum ChunkState {
    AwaitingSize,
    ReadingData(usize),
    AwaitingTrailer,
    Done,
}
```

**API:**
- `async fn read(&mut self, dest: &mut [u8]) -> Result<usize, HttpError>` — decoded body bytes, 0 at end.
- `async fn read_all(&mut self, limit: usize) -> Result<Vec<u8>, HttpError>` — convenience.
- `fn is_finished(&self) -> bool`

**100-Continue:** Sent lazily on first `read()` call when `Expect: 100-continue` is present. If handler never reads body, no 100 is sent.

**Handler signature change:**

```rust
fn handle(&self, req: Request, body: BodyReader<'_>, res: ResponseWriter<'_>) -> ...
```

The handler receives `BodyReader` and `ResponseWriter` but must use them sequentially: read the body first, then write the response. The `BodyReader` is consumed/dropped before `ResponseWriter` methods are called. For 0.9 and bodyless methods, `BodyReader` is a no-op with `BodyFraming::None` that returns 0 immediately.

**Error handling during body read:** If the client disconnects mid-body or sends malformed chunks, `BodyReader::read()` returns an `HttpError`. The session transitions to `Failed` and the connection closes.

## Section 5: ResponseWriter Changes

**Response state machine:**

```rust
enum ResponseState {
    Headers,
    Body,
    Finished,
}
```

**New methods:**
- `set_status(&mut self, code: u16, reason: &str)` — defaults to 200 OK if not called.
- `add_header(&mut self, name: &str, value: &str)` — buffers header.
- `write_body(&mut self, data: &[u8])` — first call flushes status + headers + `\r\n`, then body.
- `finish(self)` — finalizes response.

**Auto Content-Length vs Chunked:**
- Handler set Content-Length manually → use it, write raw.
- HTTP/1.1 + no Content-Length → inject `Transfer-Encoding: chunked`, chunk-encode writes.
- HTTP/1.0 + no Content-Length → omit, close connection after response.

**HEAD responses:** `write_body` suppressed (no-op), headers still sent with Content-Length if provided.

**HTTP/0.9 path:** `set_status` and `add_header` are no-ops, `write_body` writes raw bytes.

## Section 6: Session State Machine

Expanded states:

```rust
enum SessionState {
    AwaitingRequest,
    RequestReady,
    ReadingBody,
    ExpectContinue,
    ResponseInProgress,
    Failed,
    Done,
    AwaitingNext,
}
```

**Key transitions:**

```
AwaitingRequest → RequestReady           (head parsed)
RequestReady → ReadingBody               (handler reads body)
RequestReady → ExpectContinue            (Expect: 100-continue)
ExpectContinue → ReadingBody             (100 sent)
ReadingBody → ResponseInProgress         (body done, handler responds)
ReadingBody → Failed                     (client disconnect, malformed chunk)
RequestReady → ResponseInProgress        (no body)
ResponseInProgress → AwaitingNext        (keep-alive)
ResponseInProgress → Done               (close)
AwaitingNext → AwaitingRequest           (compact, cycle)
Any state → Failed                       (I/O error, parse error)
```

**Unconsumed body handling:** If the handler begins responding without fully consuming the request body, the session must drain remaining body bytes before the next request on a keep-alive connection. If draining fails or is impractical (e.g., large remaining body), the connection closes instead (`Done`).

**Keep-alive logic in `finish_response()`:**
- HTTP/0.9: always Done
- HTTP/1.0: Done unless `Connection: keep-alive` → AwaitingNext
- HTTP/1.1: AwaitingNext unless `Connection: close` → Done

**Buffer compaction** during `AwaitingNext → AwaitingRequest`. After compaction, all absolute offsets from the previous request are invalid. The connection must clear the stored `Request` before compacting. Request path/header offsets are only valid until the next `compact()` call.

## Section 8: Connection & Listener Changes

**HttpConnection:**
- `next_request()` — on first call with `Detecting` codec, detects version then parses. On keep-alive, parses from buffer.
- `body_reader()` — new method returning `BodyReader`.
- `respond()` — version-aware, passes version to ResponseWriter.
- 8 KiB buffer retained as intentional limitation. `RequestTooLarge` covers overflow. Real-world HTTP/1.1 requests with cookies can exceed this — buffer size can be made configurable in a future iteration.

**HttpListener:**
- `accept()` — returns connection with `HttpCodec::Detecting`.
- `serve()` — keep-alive loop: continues iterating instead of closing after one response.

**buffer.rs** — no changes needed.

## Section 9: File Organization

**New files:**
- `codec/parse.rs` — shared parsing functions
- `codec/v1_0.rs` — HTTP/1.0 codec
- `codec/v1_1.rs` — HTTP/1.1 codec

**Modified files:**
- `codec/mod.rs` — Detecting variant, new modules, re-exports
- `request.rs` — expanded Method, Version, add HeaderOffset, BodyFraming
- `response.rs` — ResponseState, set_status(), add_header(), auto chunked
- `session.rs` — new states, keep-alive logic
- `connection.rs` — body_reader(), version-aware respond(), keep-alive
- `listener.rs` — Detecting codec, keep-alive loop
- `handler.rs` — BodyReader parameter
- `error.rs` — new ParseError variants
- `mod.rs` — export new types

**Unchanged files:**
- `codec/v0_9.rs`
- `buffer.rs`

## Known Limitations & Future Work

- **8 KiB buffer cap** — may reject large real-world requests. Configurable buffer size is a future enhancement.
- **No keep-alive idle timeout** — idle connections are not closed proactively. A timeout mechanism can be added later.
- **No `Date` header injection** — RFC 9110 Section 6.6.1 recommends it but the network stack may not have wall-clock access.
- **`TRACE` method** — included in the enum but no special echo-back handling built in. Left to handler implementation.
- **No client support** — to be added in a separate design cycle.
